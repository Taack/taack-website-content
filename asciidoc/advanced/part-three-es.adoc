== Introducción

En esta sección, aprenderemos sobre seguridad y restricciones (constraints). Primero, aprenderemos cómo implementar estas restricciones, lo que nos permitirá limitar las entradas de los usuarios. Luego, profundizaremos en la seguridad creando dos tipos de usuarios: administradores y prestatarios, cada uno con acceso a diferentes funcionalidades.

Los administradores podrán:

- añadir, eliminar y reactivar autores en el menú Author.
- añadir libros en el menú Book.
- comprar y eliminar ejemplares (`bookInstances`) en el menú Book.
- tener acceso a la lista de usuarios y a la información sobre cada uno de ellos en el menú User.
- aprobar libros en el menú Borrowed.

Los prestatarios podrán:

- ver los autores en el menú Author.
- ver los libros en el menú Book.
- solicitar un ejemplar (`bookInstance`) en el menú Book.
- devolver un ejemplar (`bookInstance`) en el menú Borrowed.
- ver sus solicitudes anteriores en el menú History.

== Restricciones (Constraints)

Si un administrador está aprobando una solicitud, no tendría sentido que pudiera aprobar el libro en una fecha anterior a la fecha en que se realizó la solicitud; no se le debería permitir hacer eso. Lo mismo ocurre con la fecha en que el usuario devuelve el libro: no debería poder devolverlo antes de la fecha de aprobación. Implementemos esto en `MyLibraryBorrowed`.

.Diagrama de clases para su comodidad

Necesitamos implementar restricciones en nuestras entidades de dominio para asegurarnos de proporcionar datos coherentes y lógicos a nuestra biblioteca.

Intente añadir una restricción `nullable` en las fechas de préstamo, con un validador (la fecha de aprobación debe ser posterior o igual a `requestDate`, y `returnDate` debe ser posterior o igual a la fecha de aprobación del préstamo).

.Solución
[%collapsible]
====
.Añada las siguientes restricciones:
[,groovy]
----
static constraints = {
    approvalDate nullable: true, validator: { Date val, MyLibraryBorrowed obj ->
        if (val == null) return true
        return val >= obj.requestDate
    }

    returnDate nullable: true, validator: { Date val, MyLibraryBorrowed obj ->
        if (val == null) return true
        return val >= obj.approvalDate
    }

    bookInstance nullable:false
    user nullable:false
}
----
====
Para obtener más información, consulte la link:https://docs.grails.org/latest/ref/Constraints/Usage.html[documentación de Grails] sobre restricciones.

== Menú de Usuarios (User Menu)
Como se explicó anteriormente, también queremos tener una tabla que muestre todos los usuarios para los administradores.
Empecemos implementando `buildUsersTable` (puede utilizar la tabla de autores como ejemplo base para implementarla).

.Solución
[%collapsible]
====
[,groovy]
----
UiTableSpecifier buildUsersTable() {
    UiTableSpecifier buildUsersSpecifier = new UiTableSpecifier()
    User user = new User()

    buildUsersSpecifier.ui {
        header {
            label user.username_
            label "Authorities"
        }

        TaackFilter taackFilter = taackFilterService.getBuilder(User)
                .setSortOrder(TaackFilter.Order.ASC, user.username_)
                .setMaxNumberOfLine(10).build()

        iterate taackFilter, {User userIterator ->
            rowColumn {
                rowAction ActionIcon.SHOW * IconStyle.SCALE_DOWN, MyLibraryController.&showUser as MC, userIterator.id
                rowField userIterator.username_
            }
            rowField userIterator.authorities_
        }
    }
}
----

== Seguridad Parte 1
Genial, ahora tenemos todo lo que necesitamos. Solo nos falta añadir la capa de seguridad.
Una de las grandes ventajas de Taack es lo sencillo que resulta esto. Simplemente añadiendo `@Secured(['ROLE_ADMIN'])` encima de un método, estará protegiendo dicho método frente a cualquier usuario que no tenga el rol `ROLE_ADMIN`. `@Secured(['ROLE_ADMIN'])` no solo ocultará el icono, sino que también hará que el método sea inaccesible mediante un enlace directo.

Vamos a añadir `@Secured(['ROLE_ADMIN'])` y `@Secured(['ROLE_BORROWER'])` a los métodos necesarios. [TODO 6.1] Pista: hay un total de 11 anotaciones `@Secured` para añadir en `MyLibraryController`.

En proyectos más grandes, añadir sentencias condicionales para ocultar botones o columnas puede volverse muy complejo. Por ello, recomendamos intentar mantener el mismo número de filas/columnas en pantalla para todas las páginas o ventanas modales que utilicen el mismo builder. Para ocultar botones en este caso, puede utilizar otra técnica.
