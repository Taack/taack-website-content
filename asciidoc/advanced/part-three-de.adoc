== Einführung

In diesem Abschnitt lernen wir Sicherheit und Einschränkungen (Constraints) kennen. Zuerst erfahren wir, wie wir diese Einschränkungen implementieren, um Benutzereingaben zu begrenzen. Anschließend tauchen wir in das Thema Sicherheit ein, indem wir zwei Benutzertypen erstellen: Administratoren (Admins) und Ausleiher (Borrowers), die jeweils Zugriff auf unterschiedliche Funktionen haben.

Administratoren können:

- Autoren im Menü „Author" hinzufügen, löschen und reaktivieren.
- Bücher im Menü „Book" hinzufügen.
- Buchinstanzen (`bookInstances`) im Menü „Book" kaufen und löschen.
- im Menü „User" auf die Benutzerliste und auf Informationen zu jedem einzelnen Benutzer zugreifen.
- Bücher im Menü „Borrowed" genehmigen.

Ausleiher können:

- die Autoren im Menü „Author" einsehen.
- die Bücher im Menü „Book" einsehen.
- eine Buchinstanz (`bookInstance`) im Menü „Book" anfragen.
- eine Buchinstanz (`bookInstance`) im Menü „Borrowed" zurückgeben.
- ihre bisherigen Anfragen im Menü „History" einsehen.

== Einschränkungen (Constraints)

Wenn ein Administrator eine Anfrage genehmigt, wäre es nicht sinnvoll, wenn er das Buch zu einem Datum vor dem Anfragedatum genehmigen könnte; dies sollte nicht erlaubt sein. Dasselbe gilt für das Rückgabedatum des Buches durch den Benutzer: Er sollte es nicht vor dem Genehmigungsdatum zurückgeben können. Implementieren wir dies in `MyLibraryBorrowed`.

Wir müssen Einschränkungen (Constraints) für unsere Domänenentitäten implementieren, um sicherzustellen, dass wir konforme und logische Daten für unsere Bibliothek bereitstellen.

Versuchen Sie, eine `nullable`-Einschränkung für die Datumsfelder der Ausleihe mit einem Validator hinzuzufügen (das Genehmigungsdatum muss nach `requestDate` liegen und `returnDate` muss nach dem Genehmigungsdatum der Ausleihe liegen).

.Lösung
[%collapsible]
====
.Fügen Sie die folgenden Einschränkungen hinzu:
[,groovy]
----
static constraints = {
    approvalDate nullable: true, validator: { Date val, MyLibraryBorrowed obj ->
        if (val == null) return true
        return val >= obj.requestDate
    }

    returnDate nullable: true, validator: { Date val, MyLibraryBorrowed obj ->
        if (val == null) return true
        return val >= obj.approvalDate
    }

    bookInstance nullable:false
    user nullable:false
}
----
====
Weitere Informationen finden Sie in der link:https://docs.grails.org/latest/ref/Constraints/Usage.html[Grails-Dokumentation] über Constraints.

UiTableSpecifier buildUsersTable() {
    UiTableSpecifier buildUsersSpecifier = new UiTableSpecifier()

            label "Authorities"

                .setSortOrder(TaackFilter.Order.ASC, user.username_)

                rowAction ActionIcon.SHOW * IconStyle.SCALE_DOWN, MyLibraryController.&showUser as MC, userIterator.id

== Sicherheit Teil 1
Großartig, wir haben jetzt alles, was wir brauchen. Wir müssen nur noch die Sicherheitsebene hinzufügen.
Einer der großen Vorteile von Taack ist, wie einfach dies funktioniert. Indem Sie einfach `@Secured(['ROLE_ADMIN'])` über einer Methode einfügen, schützen Sie die Methode vor jedem Benutzer, der nicht über die Rolle `ROLE_ADMIN` verfügt. `@Secured(['ROLE_ADMIN'])` blendet nicht nur das Symbol aus, sondern macht die Methode auch über einen direkten Link unzugänglich.

Fügen wir nun `@Secured(['ROLE_ADMIN'])` und `@Secured(['ROLE_BORROWER'])` zu den entsprechenden Methoden hinzu. [TODO 6.1] Hinweis: Insgesamt müssen in `MyLibraryController` 11 `@Secured`-Annotationen hinzugefügt werden.

In größeren Projekten kann das Hinzufügen von bedingten Anweisungen zum Ausblenden von Schaltflächen oder Spalten sehr komplex werden. Deshalb empfehlen wir, nach Möglichkeit auf allen Seiten und in allen Modalfenstern, die denselben Builder verwenden, dieselbe Anzahl von Spalten/Zeilen anzuzeigen. Um Schaltflächen in diesem Fall auszublenden, können Sie eine andere Technik verwenden.
